# 项目二交付文档：策略编排与推荐大脑

## 1. 项目概述

项目二是 AI 全链路智能营销决策系统的 B 端策略中枢。它承接项目一提供的客户、产品、权益、授权、规则和行为数据，在合规约束下完成客群筛选、群像刻画、策略生成和单客推荐，并将可执行策略交给项目三的客户交互智能体。

一句话说明：

> 把原始客户数据和经营目标，转化为“向谁推荐什么、通过什么渠道、为什么推荐、C 端应该如何表达”的可解释策略。

本次交付目标是先跑通完整 MVP 闭环，而非在缺少历史投放标签的前提下假装已经具备成熟的转化预测或 ROI 优化模型。

## 2. 项目边界与协作关系

```text
项目一：知识与数据底座
  客户画像 / OneID / 意图向量 / 行为序列 / 授权与频控
  产品与权益 / 产品准入规则 / 渠道成本与指标 / 合规规则
                         |
                         v
项目二：策略编排与推荐大脑
  合规筛选 -> 候选池 -> 群像刻画 -> 打分圈选 -> 策略包与单客决策
                         |
                         v
项目三：面向客户的智能体
  首页推荐 / 查询问答 / 交互式营销 / 触达执行 / 效果反馈
                         |
                         v
项目二：反馈复盘与下一轮优化建议
```

### 2.1 项目一传入项目二的数据

| 数据类别 | 主要字段或内容 | 在项目二中的用途 |
|---|---|---|
| 客户唯一标识 | `customer_id`、`oneid` | 识别客户、向 C 端返回单客策略 |
| 客户画像 | 年龄、收入、卡等级、消费、额度使用、App 活跃等 | 群像、准入、价值评分 |
| 意图与行为 | 意图向量、近期事件序列、浏览/点击/咨询信号 | 意图匹配、行为响应评分 |
| 合规与触达 | 营销授权、免打扰、黑名单、投诉风险、历史触达 | 前置排除、渠道可用性、频控 |
| 产品和权益 | 产品目录、权益目录、产品权益映射 | 产品推荐和权益匹配 |
| 产品规则 | 年龄、收入、卡等级、额度等准入条件 | 生成客户 x 产品候选池 |
| 渠道上下文 | 渠道成本、平均打开/点击率、容量 | 渠道路由和成本解释 |

当前 MVP 通过本地 CSV 适配器读取项目一的脱敏真实数据。项目一正式 API 完成后，只需替换数据加载层，策略、群像和接口输出合同保持不变。

### 2.2 项目二传入项目三的内容

- 批量活动策略包：客群分段、渠道路由、内容方向、合规限制、实验建议。
- 单客首页推荐：推荐产品/权益、排序、推荐理由、客群标签、允许渠道。
- 对话决策：是否推荐、下一步动作、推荐产品和内容方向。
- 反馈规则：项目三回传曝光、点击、转化、投诉和 ROI，项目二输出指标摘要与优化建议。

## 3. 已交付功能

### 3.1 经营目标结构化解析

运营人员可输入自然语言目标。系统调用大模型解析目标中的产品、预算、风险偏好、频控和渠道偏好，再转换为标准 `CampaignRequest`；模型不可用时会使用规则兜底，保证主链路可运行。

- 接口：`POST /api/strategy/parse-goal`
- 产物：`goal`、`product`、`budget_wan`、`risk_level`、`frequency_level`、`channel_mode` 等结构化字段。

### 3.2 合规筛选与可解释准入

在任何打分或推荐前，系统先检查营销授权、免打扰、黑名单、高风险、渠道授权和频控等条件；未通过的客户或渠道会附带排除原因，避免“分数高就一定推荐”的错误。

- 接口：`POST /api/strategy/eligibility/real-data`
- 本轮离线数据结果：8,000 名原始客户中，6,860 名通过客户级合规筛选。
- 输出：合规汇总、客户判定、允许渠道、拦截原因样本。

### 3.3 候选池构建

候选池的基本单位不是单纯的“一个客户”，而是：

```text
合规客户 x 符合准入的产品/权益 x 可触达渠道
```

系统先检查客户级合规，再检查产品级准入和渠道级授权，输出候选记录、渠道成本、历史渠道指标和阻断原因。这为后续完善 `StrategyScore(customer, product, channel)` 多维排序准备了统一输入。

- 接口：`POST /api/strategy/candidates/real-data`
- 输出：合格候选样本、各产品/渠道候选数量、被拦截原因、渠道成本和点击指标。

### 3.4 KMeans 群像刻画

群像用于找出“同类客户”，从而让不同人群使用不同的打分重点、产品方向、渠道策略和内容表达。当前使用 KMeans，并对下列六维特征标准化后聚类：

1. 与目标产品匹配的意图分数。
2. 月均消费。
3. 额度使用率。
4. App 活跃天数。
5. 近期相关行为。
6. 投诉风险。

选 K 不是手工固定。系统计算 `K=2~8` 的惯性值和轮廓系数；由于 `K=2` 虽然更粗粒度地分开了客户，但不支持精细运营，因此以 `K=3~8` 作为运营可选范围。`K=5` 在该范围内轮廓系数最高（0.3122），最小簇规模为 313，最终被设为系统默认值。

- 完整依据：[KMeans 选 K 报告](kmeans_k_selection_report.md)
- 本轮进入 KMeans 的合规候选客户：6,805 名。
- 重要说明：当前数据中的投诉风险为零方差，因此它仍作为合规前置规则保留，但暂时不贡献于客户之间的聚类差异。数据特征或业务场景变化后，应重新运行选 K 脚本。

### 3.5 差异化打分、客群圈选与策略生成

群像完成后，系统按不同群像使用不同的评分权重。评分综合意图、近期行为、客户价值、活跃度、历史响应、额度使用和风险；再依据群像配置进行配额分配和客户排序，选出预算容量内的目标客群。

批量策略生成同时输出：

- 客群规模、客群特征、预估转化/价值等解释字段。
- 客群对应的产品/权益方向。
- 渠道路由、触达顺序、渠道成本和频控约束。
- 面向 C 端的内容方向和客群映射。
- A/B 实验建议、合规限制和回调配置。

- 接口：`POST /api/strategy/generate/real-data`
- 标准策略包合同：[strategy_to_marketing.schema.json](../contracts/strategy_to_marketing.schema.json)

### 3.6 面向项目三的单客策略服务

项目三不需要拿到或保存完整客户画像，只传入 `oneid` 和当前对话上下文。项目二在服务端完成合规、群像、产品准入和排序后返回最小必要策略信息。

| 场景 | 接口 | 项目三得到的结果 |
|---|---|---|
| 客户主动进入智能体首页 | `GET /api/strategy/customers/{oneid}/recommendations?scene=agent_home&limit=5` | 最多 5 张个性化推荐卡片，包括产品、权益、理由、客群和允许渠道 |
| 客户问到某产品或表达需求 | `POST /api/strategy/decision` | 是否推荐、下一步动作、推荐产品/权益、内容方向和合规提醒 |
| C 端完成一次活动或触达 | `POST /api/strategy/feedback` | CTR、转化率、投诉率、ROI 摘要和优化建议 |

详细字段见：[B to C Online Strategy API](b_to_c_online_strategy_api.md)。

## 4. 核心决策流程

```text
运营目标 / C 端单客请求
        |
        v
目标解析与参数校验
        |
        v
客户、产品、权益、授权、行为、渠道数据
        |
        v
合规和产品准入筛选
        |
        v
KMeans 群像（默认 K=5）
        |
        v
群像差异化评分、候选排序、预算容量控制
        |
        v
产品/权益/渠道/内容策略生成
        |
        +--> 批量策略包给运营和 C 端
        |
        +--> 单客推荐与对话决策给 C 端
        |
        v
曝光、点击、转化、投诉、ROI 回流 -> 复盘建议
```

## 5. 接口清单

| 接口 | 用途 | 主要调用方 |
|---|---|---|
| `POST /api/strategy/parse-goal` | 自然语言经营目标解析 | B 端运营页面 |
| `POST /api/strategy/eligibility/real-data` | 基于项目一数据执行合规筛选 | B 端运营页面 |
| `POST /api/strategy/candidates/real-data` | 生成客户 x 产品 x 渠道候选池 | B 端策略引擎 |
| `POST /api/strategy/generate/real-data` | 生成完整批量营销策略和 B-C 策略包 | B 端运营页面 |
| `GET /api/strategy/customers/{oneid}/recommendations` | 首页个性化推荐 | 项目三智能体 |
| `POST /api/strategy/decision` | 对话过程中的推荐决策 | 项目三智能体 |
| `POST /api/strategy/feedback` | 接收效果反馈并输出优化建议 | 项目三/运营复盘 |
| `GET /health` | 健康检查 | 联调与部署 |

## 6. 已验证结果与质量保证

- 已使用项目一提供的本地脱敏数据跑通合规筛选、群像刻画、批量策略和单客推荐。
- 选 K 脚本固定随机种子，并对全量候选客户计算惯性值、对固定样本计算轮廓系数，结果可复跑。
- 自动化测试覆盖目标解析兜底、合规筛选、策略包、KMeans 群像、B-C 单客推荐、候选池和反馈复盘；当前 17 项测试通过。
- 对未知 `oneid`、无营销授权或不满足准入条件的客户，接口返回明确的错误、空推荐或不推荐结果，不绕过合规规则。

## 8. 当前限制与后续迭代

| 当前 MVP 已实现 | 下一阶段优化 |
|---|---|
| 基于规则、画像和意图的可解释评分 | 使用历史活动标签训练响应率、转化率、流失风险和 uplift 模型 |

| 指标摘要和规则型复盘建议 | 真实归因、A/B 检验、显著性分析和策略自动调参 |
| 本地 CSV 适配器 | 替换为项目一正式 API、数据库、审计日志和模型监控 |

答辩时应明确：项目二已经完成可运行、可解释、可联动的策略 MVP；模型训练和真正 ROI 最优化需要补充“活动-触达-转化-成本-收益”闭环数据后再进行，不能用静态模拟数据宣称已经训练完成。
