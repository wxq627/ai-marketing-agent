# 项目 B：Strategy Agent 详细实施蓝图

## 0. 项目 B 到底负责什么

项目 B 是“策略编排与推荐大脑”。它不保存企业知识，也不直接和客户聊天；它负责把项目一提供的客户洞察、产品规则和合规边界，转成项目三可以执行的营销策略，并根据反馈不断优化。

```text
项目一 Knowledge Agent                         项目二 Strategy Agent                         项目三 Marketing Agent
客户画像、事件、意图、产品规则、合规规则  ->  圈选客群、生成策略、预算渠道、解释  ->  与客户交互、执行触达、回传结果
```

项目 B 的最终交付不是一段聊天回答，而是一份可审计的 `Strategy Package`：谁可触达、给什么权益、走什么渠道、花多少预算、频率限制是什么、为什么这么推荐、怎样做对照实验。

## 1. 推荐的总体架构

```text
运营目标（自然语言）
    -> 目标解析器
    -> 合规与规则闸门
    -> 特征加工 / 意图消费
    -> 客群圈选与评分
    -> 群像报告生成
    -> 策略、渠道、预算编排
    -> 策略解释与人工确认
    -> B -> C 标准策略包
    -> C -> B 效果反馈与复盘
```

建议采用“确定性决策引擎 + LLM 增强层”的混合架构：

- 规则、人数、金额、频控、授权、风险、预算约束：由 Python/数据库/优化算法计算。
- 文本理解、意图抽取、群像叙述、运营需求解析、策略追问：由 LLM 完成。

这样既有 AI 能力，也不让 LLM 成为不可控的黑盒筛人器。

## 2. 开发顺序总览

| 阶段 | 要解决的问题 | 产物 | 是否 MVP 必需 |
| --- | --- | --- | --- |
| 1 | B 到底收什么、发什么 | 数据字典、JSON Schema、Mock 数据 | 是 |
| 2 | 哪些客户根本不能触达 | 合规/频控/风险准入器、排除日志 | 是 |
| 3 | 如何理解客户与活动 | 特征表、意图标签、目标解析结果 | 是 |
| 4 | 如何形成“值得投放”的客群 | 客群评分、名单、群像报告 | 是 |
| 5 | 如何把客群变成具体策略 | 权益/渠道/预算/A-B 实验方案 | 是 |
| 6 | 如何让运营人员信任结果 | 推荐理由、模拟重算、人工确认 | 是 |
| 7 | 如何交给 C 端执行 | 标准策略包、下发接口 | 是 |
| 8 | 如何知道策略是否有效 | 反馈接口、活动看板、复盘报告 | 是，先做简版 |
| 9 | 如何体现进阶算法能力 | Uplift、聚类、约束优化、RAG | 加分项 |

后文每一阶段都包含：要做什么、输入输出、候选技术方案、推荐选择、验收标准。

## 3. 阶段 1：确定数据合同与数据字典

### 要做什么

把“项目一给什么”和“项目三需要什么”写成机器可校验的合同，避免三个人最后对不上字段。

### 输入与输出

**A -> B 输入核心对象**：

```json
{
  "customer_id": "C001",
  "customer_profile": {
    "marketing_consent": true,
    "monthly_spend": 8200,
    "credit_limit_usage": 0.66,
    "lifecycle_stage": "active",
    "value_level": "high",
    "complaint_risk": 0.05,
    "recent_contact_count": 1,
    "preferred_channel": "app_push",
    "tags": ["high_spend", "app_active"]
  },
  "intent_vector": {"installment_interest": 0.81},
  "event_sequence": []
}
```

**B -> C 输出核心对象**：

```json
{
  "campaign_id": "CMP_001",
  "audience": {"segment_id": "SEG_001", "customer_ids": ["C001"]},
  "action": {"product": "installment", "benefit": "fee_discount"},
  "channel_plan": [{"channel": "app_push", "priority": 1}],
  "frequency_cap": {"max_contacts_7d": 2},
  "experiment_plan": {"control_ratio": 0.1}
}
```

**C -> B 反馈核心对象**：`exposure`、`click`、`conversion`、`reject`、`unsubscribe`、`complaint`、`cost`、`revenue`、`event_time`。

### 候选方案

| 方案 | 做法 | 为什么好 | 代价/风险 |
| --- | --- | --- | --- |
| A. Markdown 文档约定 | 三人手动阅读字段说明 | 最快，适合刚开始讨论 | 容易拼错字段，无法自动校验 |
| B. JSON Schema | 用 schema 定义必填字段、类型、枚举值 | 前后端都能自动校验；仓库已经具备基础 | 需维护 schema 版本 |
| C. OpenAPI | 为每个 HTTP 接口声明请求/响应格式 | 可自动生成接口文档，联调方便 | 初期写法稍多 |
| D. Protobuf/Avro | 强类型事件契约 | 高吞吐、适合生产事件流 | 训练营项目过重 |

### 推荐选择

选择 **B + C**：用 JSON Schema 管数据对象，用 OpenAPI/接口文档描述 HTTP 调用。你们仓库已有 `contracts/*.schema.json`，只需继续补齐字段与示例。

### 完成标准

1. 三个方向各有一份 schema 和一份合法示例 JSON。
2. B 端能拒绝缺少必填字段的请求，并返回可读错误。
3. 所有字段都标明来源、类型、是否必填、更新时间和用途。

## 4. 阶段 2：合规、权限与频控闸门

### 要做什么

在任何评分和推荐前，先筛掉不应该触达的人，并记录每种排除原因。它是银行营销系统的第一道门。

### 规则示例

```text
marketing_consent = false              -> 排除：未营销授权
recent_contact_count >= 2（近 7 天）    -> 排除：频控命中
complaint_risk >= 0.7                  -> 排除：高投诉风险
risk_level in [high, blacklist]        -> 排除：风险/合规限制
already_owns_target_product = true     -> 排除：产品不适配
```

### 候选方案

| 方案 | 做法 | 为什么好 | 适用时机 |
| --- | --- | --- | --- |
| A. Python if/else 规则 | 在代码中写明确条件 | 最容易理解和演示；MVP 最快 | 当前首选 |
| B. YAML/JSON 规则配置 | 把阈值和规则放入配置文件 | 不改代码就能调阈值；便于运营侧理解 | 第二步即可加入 |
| C. 规则引擎 | 使用 Drools/自建规则 DSL | 规则多、版本多时更易维护 | 真实生产或规则极多时 |
| D. LLM 判断规则 | 让模型阅读规则后决定是否放行 | 面对模糊文本时有补充价值 | 不可作为硬准入主方案 |

### 推荐选择

先用 **A + B**：代码实现稳定逻辑，阈值写到 `config/rules.json`。LLM 只可辅助解释“为何排除”，不能绕过规则。

### 完成标准

1. 每个客户得到 `eligible: true/false` 和 `exclusion_reasons`。
2. 群像报告能显示“候选 10,000 人，未授权排除 1,200 人”等统计。
3. 任意策略都无法跳过营销授权和频控规则。

## 5. 阶段 3：目标解析与特征加工

这是把“运营想做什么”和“客户最近在表达什么”变成可计算字段的阶段。

### 3.1 运营目标解析

运营输入：

> 面向高消费、近期对分期感兴趣的客户做分期促活，预算 20 万，投诉风险低，优先 App。

输出：

```json
{
  "goal": "installment_conversion",
  "product": "installment",
  "audience_hints": ["high_spend", "installment_interest"],
  "budget": 200000,
  "channel_preference": ["app_push"],
  "risk_preference": "low"
}
```

#### 候选方案

| 方案 | 为什么好 | 不足 |
| --- | --- | --- |
| A. 关键词/正则 | 不依赖模型、可控、最快 | 表达变化时脆弱 |
| B. LLM + JSON Schema | 用户能自由表达，输出仍受字段约束 | 要做 prompt 和 schema 校验 |
| C. 微调意图分类模型 | 大量固定需求时速度快、一致性高 | 需要较多标注样本 |

**推荐：B，并保留 A 兜底。** 这是 B 端最自然的 LLM 使用点：LLM 负责读懂需求，后端负责验证金额、渠道、产品和规则。

### 3.2 客户文本/事件特征加工

原始文本或事件不应直接拿去投放，需要加工成统一标签：

```text
“账单可以分 12 期吗？” -> installment_interest: 0.90
“不要再发促销短信”       -> do_not_contact_signal: true
“下周去日本，境外刷卡...”  -> travel_interest: 0.86
```

#### 候选方案

| 方案 | 为什么好 | 不足 |
| --- | --- | --- |
| A. 关键词词典 | 可审计、对少量意图很有效 | 覆盖不足，难懂口语表达 |
| B. LLM 结构化抽取 | 读懂开放式对话；可给原文证据 | 需做置信度和抽样复核 |
| C. Embedding 相似度匹配 | 性能好，适合大量相似意图 | 需维护意图样例和阈值 |
| D. 监督分类模型 | 大规模稳定、成本低 | 需要已标注语料 |

**推荐：MVP 用 A + B；有反馈数据后升级为 D。** LLM 必须只输出限定标签字典、置信度与原文证据，低置信度不直接影响营销准入。

### 完成标准

1. 一句运营需求可以转换为合法的 `CampaignRequest` JSON。
2. 一段客户文本可以转换为标签、意图分数、置信度、证据。
3. 无法识别或低置信度文本进入 `unknown`，不能被模型杜撰。

## 6. 阶段 4：客群圈选与群像刻画

### 要做什么

在通过合规闸门的人群中，根据活动目标选出最适合的一批，并总结“这批人是谁、为什么值得投放”。

### 4.1 圈选/排序候选方案

| 方案 | 做法 | 为什么好 | 局限 |
| --- | --- | --- | --- |
| A. 规则分群 | 条件组合，如高消费 + 分期意图 + App 活跃 | 最清楚、最好解释 | 覆盖不了复杂关系 |
| B. RFM/RFMC + 生命周期 | 用最近消费、频次、金额、额度使用等分层 | 与信用卡经营强相关，业务好讲 | 不直接包含当前意图 |
| C. 多维加权评分 | 价值、意图、渠道、转化、风险各得分再加权 | 可排序、可调策略、MVP 很实用 | 权重需要业务解释 |
| D. 监督学习预测 | 预测响应/转化/投诉概率 | 历史数据足够时更准确 | 需要有标签和评估集 |
| E. Uplift 增量模型 | 预测触达带来的额外转化 | 最符合 ROI，答辩很有亮点 | 必须有随机对照组 |
| F. 无监督聚类 | 自动发现相似客户群 | 可发现未知群体 | 不保证业务可执行或合规 |

### 推荐选择

**MVP 采用 A + B + C。**

```text
先合规过滤
-> 计算价值、活跃、意图、渠道、风险分数
-> 多维加权排序
-> 截取 Top N / 高于阈值的客户
-> 用 RFM 与生命周期给群体打业务标签
```

这是足够“算法化”、可解释、可在 mock 数据上稳定演示的方案。D、E、F 留为项目亮点升级，不要一开始就压在主链路上。

### 4.2 群像报告候选方案

| 方案 | 做法 | 为什么好 | 推荐度 |
| --- | --- | --- | --- |
| A. 程序模板 | 根据统计字段拼接固定句子 | 数字绝不乱、稳定 | 必做兜底 |
| B. LLM 群像解释器 | 将聚合统计输入 LLM，输出摘要、理由、风险提示 | 运营体验好，体现 LLM | 强烈推荐 |
| C. 文本向量 + 聚类 + LLM 命名 | 自动发现客户咨询主题，再命名群体 | 算法展示很强 | 数据多时加入 |
| D. LLM 逐客分群 | 将每个客户交给模型判断 | 开发看似简单 | 不稳定、不适合名单准入 |

**推荐：A + B。** 先由程序生成可靠统计，LLM 只能依据这些统计生成自然语言解释；不要让 LLM 修改人数、金额、风险结论。

### 推荐群像输出

```json
{
  "segment_name": "高价值活跃分期潜力客群",
  "eligible_count": 8020,
  "targeted_count": 2000,
  "top_tags": ["high_spend", "app_active", "installment_interest"],
  "lifecycle_distribution": {"active": 0.72, "growth": 0.28},
  "channel_preference": {"app_push": 0.61, "wechat": 0.24},
  "exclusion_summary": {"no_consent": 1200, "frequency_cap": 600},
  "business_interpretation": "高消费且近期表达分期意图，建议优先 App 触达。"
}
```

### 完成标准

1. 同一个活动输入可以得到确定的目标名单、排序分数和入选理由。
2. 群像包含规模、特征、渠道、风险和排除统计。
3. 运营人员能理解每个分数由什么组成，并能调整权重或阈值后重算。

## 7. 阶段 5：策略、权益、渠道与预算编排

### 要做什么

不止选人，还要决定“给什么、在哪发、何时发、花多少钱、保留多少人做对照”。

### 5.1 权益推荐候选方案

| 方案 | 为什么好 | 推荐 |
| --- | --- | --- |
| A. 产品-客群规则矩阵 | 例如分期意图高 -> 手续费优惠 | 可控、符合产品规则 | MVP 首选 |
| B. 相似客群历史表现 | 查相似客群过去对哪种权益转化高 | 用数据优化 | 有反馈后加入 |
| C. 协同过滤/推荐模型 | 找相似客户喜欢的权益 | 个性化强 | 数据量和冷启动要求高 |
| D. LLM 直接编权益 | 文案灵活 | 可能违反产品和合规规则 | 只能生成文案建议，不能定权益 |

**推荐：A 起步，B 升级。** 权益资格和费率只能从项目一的规则库中选择，不能由 LLM 编造。

### 5.2 渠道路由候选方案

| 方案 | 为什么好 | 推荐 |
| --- | --- | --- |
| A. 客户偏好规则 | `preferred_channel` + 渠道可用性 | 直接、可靠 | MVP 首选 |
| B. 历史渠道响应率 | 针对客户/客群比较 Push、短信、企微的打开点击 | 更精细 | 有足够日志后 |
| C. Contextual Bandit | 边投放边探索最优渠道 | 很有算法特色 | 需稳定回传和探索预算 |

### 5.3 预算分配候选方案

| 方案 | 做法 | 为什么好 | 推荐 |
| --- | --- | --- | --- |
| A. 固定比例 | Push 60%、企微 30%、短信 10% | 简单，Demo 稳定 | MVP |
| B. 按预估 ROI 比例 | 将更多预算给高 ROI 渠道/客群 | 与经营目标一致 | 第二阶段 |
| C. 约束优化 | 在预算、渠道容量、频控下最大化预估收益 | 体现运筹优化能力 | 加分项 |

### 5.4 实验方案候选方案

| 方案 | 为什么好 | 推荐 |
| --- | --- | --- |
| A. 固定 10% 随机对照组 | 容易解释和实现，可估计增量 | MVP 必做 |
| B. 分层随机对照 | 按价值/生命周期分层再随机 | 更公平、更可靠 | 第二阶段 |
| C. 多臂老虎机 | 自动动态分配策略 | 探索效率高 | 不适合首版 |

### 完成标准

1. 每份策略都有产品、权益、渠道、预算、频控和对照组配置。
2. 所有权益均可追溯到项目一产品规则。
3. 预算之和不超过活动预算，渠道与频控均通过校验。

## 8. 阶段 6：策略解释、追问与人工确认

### 要做什么

让运营人员不只是看到结果，也能问“为什么”“如果预算减少会怎样”。

### 候选方案

| 方案 | 做法 | 为什么好 | 推荐 |
| --- | --- | --- | --- |
| A. 规则命中说明 | 列出分数、标签、排除和渠道原因 | 可靠、必须保留 | MVP 必做 |
| B. LLM 根据事实生成解释 | 输入已计算好的结果，生成运营语言 | 自然、适合答辩 | MVP 推荐 |
| C. What-if 重算 API | 用户改预算/渠道/风险阈值，后端重新计算 | 真正有决策产品感 | MVP 推荐 |
| D. RAG 工具调用 Agent | LLM 调用规则、报表、历史活动接口回答追问 | Agent 亮点最强 | 加分项 |

### 推荐选择

使用 **A + B + C**。例如，用户把预算从 20 万改为 10 万，系统不是让 LLM 猜结果，而是调用 `POST /api/strategy/generate` 重新计算；LLM 只解释前后差异。

### 完成标准

1. 每一条推荐至少有三条事实依据。
2. 改动预算、渠道或风险阈值后，系统能给出新策略和差异说明。
3. 策略状态有 `draft -> reviewed -> approved -> deployed`，下发前需人工确认。

## 9. 阶段 7：下发给项目三

### 要做什么

让项目三按策略对单个客户执行查询、服务或营销对话，并在触达前再次检查频控和授权。

### 候选接口形态

| 方案 | 为什么好 | 推荐 |
| --- | --- | --- |
| A. REST API + JSON | 直观、调试方便、当前项目已有雏形 | MVP 首选 |
| B. 消息队列事件 | 解耦、支持异步大量投放 | 有部署条件时升级 |
| C. 共享数据库 | 上手看似快 | 模块耦合严重，不推荐 |

### 推荐接口

```text
POST /api/strategy/generate                 生成策略
POST /api/strategy/generate-from-insight    消费项目一洞察并生成策略
POST /api/strategy/package                  生成/获取 B -> C 标准策略包
POST /api/strategy/feedback                 接收项目三效果反馈
POST /api/strategy/recalculate              What-if 重算（待实现）
```

### 完成标准

1. 项目三只用策略包就能知道对哪个客户执行什么动作。
2. 策略包有版本号、有效期、回调地址、频控与合规信息。
3. 项目三反馈可关联回 `campaign_id`、`strategy_version`、`segment_id`。

## 10. 阶段 8：反馈复盘与持续优化

### 要做什么

把“曝光了多少、点了多少、办了多少、投诉多少”转成下一轮策略调整建议。

### 候选方案

| 方案 | 为什么好 | 推荐 |
| --- | --- | --- |
| A. 指标聚合报表 | 计算触达、点击、转化、投诉、ROI | 每个活动都需要 | MVP 必做 |
| B. A/B 对照分析 | 比较策略组与对照组的转化差 | 能回答“营销是否真的有效” | MVP 必做 |
| C. 归因/增量模型 | 更准确估计策略效果 | 数据成熟后更科学 | 第二阶段 |
| D. 自动调权/强化学习 | 系统持续学习分配策略 | 很有前沿感 | 不适合首版 |

### 最小复盘指标

```text
触达人数、曝光率、点击率、转化率、拒绝率、投诉率、渠道成本、收入、ROI、
策略组-对照组转化差、策略组-对照组投诉差
```

### 完成标准

1. 同一活动可以按客群、渠道、权益和文案维度看指标。
2. 系统输出至少一条数据驱动的优化建议，例如“短信投诉率高，下一轮降低其预算比例”。
3. 复盘结果能写回下一轮策略的权重/阈值建议，但不自动越过人工审批。

## 11. 阶段 9：进阶算法加分项

这些不应阻塞 MVP，但任选一到两个做深，会让项目明显更有竞争力。

| 加分点 | 做法 | 为什么有价值 | 前置条件 |
| --- | --- | --- | --- |
| LLM 意图抽取闭环 | C 端聊天 -> 项目一标签 -> B 端策略变化 | 三模块 AI 联动最直观 | 有对话 mock 数据 |
| 向量聚类 + LLM 命名 | 发现未知咨询主题客群 | 有“自动发现群像”的算法感 | 至少几十/上百条文本 |
| Uplift 建模 | 估计触达带来的增量转化 | 最贴近营销 ROI | 随机对照组与足够反馈 |
| 预算约束优化 | 最大化预估收益，受预算/频控/渠道容量限制 | 同时体现算法与业务 | 有各渠道成本收益假设 |
| RAG 策略追问 Agent | LLM 调用规则/报表/活动工具回答追问 | Agent 产品感强 | 已有稳定接口 |
| SHAP 可解释预测 | 展示转化/风险分数的主要因子 | 增强可信度 | 有监督模型 |

## 12. 最推荐的 MVP 组合

如果你只负责 B 端，而且时间有限，我建议明确锁定如下范围：

```text
1. JSON Schema 数据合同
2. 合规、授权、风险、频控闸门
3. LLM 解析运营目标为结构化 CampaignRequest
4. LLM 从对话/搜索文本抽取受限意图标签
5. 规则 + RFM/生命周期 + 多维评分圈选
6. 程序计算群体统计，LLM 写群像解释
7. 规则矩阵生成权益、渠道、预算与 10% 对照组
8. B -> C 策略包与 C -> B 反馈接口
9. 基础复盘报表与下一轮优化建议
```

这一版已经完整覆盖了“AI 全链路智能营销决策”的 B 端职责：理解需求、理解客户、选人、出策略、可解释、可执行、可复盘。

## 13. 你现在需要做的三个选择

不是所有候选项都要今天定完。首先确定这三个，会直接决定后续代码结构：

1. **群像主方法**：只做“规则 + 评分 + LLM 报告”，还是加“文本向量聚类 + LLM 命名”？
2. **LLM 接入范围**：只做运营目标解析和群像解释，还是再加客户对话意图抽取？
3. **展示重点**：优先做 B 端自然语言圈选 Agent，还是优先做反馈 A/B 复盘与 Uplift 设计？

我的建议是：

```text
群像主方法：规则 + 评分 + LLM 报告（MVP），文本聚类作为加分项
LLM 接入范围：运营目标解析 + 客户意图抽取 + 群像解释
展示重点：先 B 端自然语言圈选 Agent，再补 A/B 复盘
```

## 14. 代码落点建议

基于当前仓库 `services/strategy-agent`，后续实现可按下面组织：

```text
ai_marketing/
  models.py                 # Customer、CampaignRequest、MarketingPlan 等数据类
  knowledge_adapter.py      # A -> B 客户洞察适配
  compliance.py             # 授权、风险、频控与排除原因
  features.py               # RFM、生命周期、标签、意图特征加工（待新增）
  llm_adapter.py            # LLM JSON 输出与 schema 校验（待新增）
  audience_profiler.py      # 群像聚合、排除统计、群像报告（待新增）
  recommender.py            # 客群评分与排序
  optimizer.py              # 渠道、预算、对照组分配
  strategy_package.py       # B -> C 标准策略包
  analytics.py              # C -> B 反馈聚合与 A/B 复盘（待新增）
  orchestrator.py           # 串联整条工作流
```

每完成一个模块都应补一组 Mock 数据、一个单元测试、一个接口样例。这样项目不会在联调时变成一团难以定位的问题。
