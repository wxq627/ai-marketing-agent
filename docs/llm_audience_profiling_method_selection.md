# LLM 群像刻画方法拆解与选型

## 1. 先把一个关键误解讲清楚

“用 LLM 刻画群像”至少可能指六件完全不同的事：

1. 从客户对话、咨询、投诉、浏览文本中读懂客户在说什么。
2. 把文本转成语义向量，再把相似客户聚成群。
3. 根据一堆表格数据，替运营人员生成一段“这群人是什么样”的解释。
4. 让运营人员用自然语言描述想找的人，LLM 转成筛选条件。
5. 让 LLM 逐个判断客户属于哪个营销人群。
6. 让 LLM 查规则、查客群统计、查历史活动后给出策略建议。

它们看起来都像“LLM 群像”，但在可靠性、成本、实现难度和适用场景上差别很大。

最重要的原则：**LLM 擅长理解文字、归纳解释和调用工具；精确的客户准入、计数、金额、排序、频控与合规判断，必须由规则、数据库查询或传统模型完成。**

原因很简单：银行营销中，系统不能因为一句自然语言就把“近 30 天消费 5,000 元”误理解成 3,000 元，更不能凭空给客户补标签。LLM 应当被约束在明确输入、明确工具和结构化输出之中。

## 2. 方法一：LLM 结构化信息抽取

### 它在做什么

把原本读不动的文本，变成系统可计算的标签和字段。

输入可以是：

- 客服对话摘要：`我下个月要出国，想知道机场贵宾厅怎么用。`
- App 搜索词：`分期手续费`、`积分兑换`
- 客户投诉/反馈：`不要再给我发短信了`
- 活动回复：`有 6 期免息吗？`

让 LLM 只返回固定 JSON：

```json
{
  "intent": "travel_benefit_inquiry",
  "product": "airport_lounge",
  "sentiment": "neutral",
  "marketing_sensitivity": "unknown",
  "do_not_contact_signal": false,
  "confidence": 0.92,
  "evidence": "想知道机场贵宾厅怎么用"
}
```

这条结果再被写入项目一的 `intent_vector` 或 `tags`，供项目 B 圈选和生成策略。

### 它产生的群像变化

原来系统只知道“客户近 30 天消费 8,000 元”；现在还知道“这批客户近期频繁咨询出行权益”。因此 B 端可以形成：

> 高消费、近期出行权益意图强、App 活跃的客户群，适合推荐商旅权益而非泛促销。

### 优点

- 最符合 LLM 的长处，价值直观。
- 能把项目三 C 端聊天内容回流给项目 B，体现三模块闭环。
- 不需要大量带标签历史数据，少量示例和明确 schema 就能先跑 Demo。
- 输出有 `evidence`，容易解释“为什么给这位客户打上该标签”。

### 风险和控制方式

- 风险：LLM 可能误判或过度推断。
- 控制：限定标签字典；要求引用原文证据；使用置信度阈值；低置信度不进入营销圈选；人工抽样复核。
- 严禁：让 LLM 从文本自行推断敏感个人信息或信用风险。

### 开发难度与项目匹配度

难度：低到中。项目匹配度：很高。它最适合作为你们项目 B 的“LLM 入口能力”。

## 3. 方法二：文本向量 + 聚类 + LLM 命名（最像“AI 自动发现群像”）

### 它在做什么

这是最标准的“从大量文本中自动发现客群主题”的方案，但它其实是三段式，而不是让聊天大模型直接分组：

```text
客户的咨询/搜索/反馈文本
    -> Embedding 向量模型：每条文本变成数字坐标
    -> 聚类算法：相似坐标自动聚成若干组
    -> LLM：阅读每组代表文本，生成群名、特征与策略解释
```

例如，系统收集 3,000 条对话/搜索：

| 聚类结果 | 代表文本 | LLM 命名后的群像 |
| --- | --- | --- |
| Cluster 0 | “分期手续费”“账单能分几期” | 分期费用关注客群 |
| Cluster 1 | “机场贵宾厅”“境外刷卡” | 商旅权益意图客群 |
| Cluster 2 | “为什么扣年费”“取消短信” | 服务/负反馈敏感客群 |

LLM 最后输出的是：

```json
{
  "cluster_id": 1,
  "segment_name": "商旅权益意图客群",
  "key_needs": ["机场贵宾厅", "境外支付", "出行保险"],
  "sentiment": "neutral_to_positive",
  "marketing_recommendation": "优先推荐出行权益，避免直接推销高门槛产品",
  "representative_evidence": ["下周去新加坡，贵宾厅怎么用？", "境外刷卡有返现吗？"]
}
```

### 为什么不让 LLM 直接“看 3,000 条文本然后分群”

直接把大量文本塞给 LLM，成本高、上下文有限、每次结果可能变，而且难以稳定给每个新客户归类。向量模型负责“相似度和规模”，LLM 负责“语言理解和命名解释”，职责更清楚。

研究中也有这种思路：使用 LLM/文本嵌入完成聚类，再基于结果构建消费者画像；LLM 辅助的主题建模与聚类也被用于从客户评价中发现偏好异质性。[Consumer segmentation with large language models](https://www.sciencedirect.com/science/article/pii/S0969698924003746)；[LLM、BERTopic 与多维聚类结合的研究](https://www.sciencedirect.com/science/article/pii/S0148296326003498)。

### 推荐技术组合

```text
中文文本
  -> bge-m3 / text embedding 模型
  -> UMAP 降维（可选）
  -> HDBSCAN 或 K-Means 聚类
  -> LLM 按 JSON Schema 命名群像、总结需求、给策略建议
```

- `K-Means`：你需要固定 4-6 个客群时选它，最适合 Demo。
- `HDBSCAN`：不想预先指定群数、允许“无法归类”文本为噪声时选它，更贴近真实文本。
- `BERTopic`：将 embedding、聚类、主题词提取封装起来，适合“客户咨询主题发现”这一展示场景；LLM 可进一步把机器主题词改成运营能懂的群名。

### 优点

- 视觉和算法展示效果最好：可以展示“原始对话 -> 自动发现主题 -> 客群画像”。
- 能发现你事先没有写规则的新需求。
- 天然适合接项目三的对话反馈，体现闭环。

### 局限

- 它发现的是“文本主题相似”，不等于“客户价值相似”或“能营销”。
- 如果文本量很少、内容很短，聚类不稳定。
- 聚类得到的群必须再叠加授权、风险、频控、价值等结构化条件才能投放。

### 开发难度与项目匹配度

难度：中。展示亮点：最高。适合你们有几十到几百条 mock 对话、希望体现“AI”而不是只做规则筛选的情况。

## 4. 方法三：LLM 群像报告生成（已有客群后的“解释器”）

### 它在做什么

先由规则、SQL 或评分模型得到一个确定的客群，再把群体统计表交给 LLM。LLM 不决定“谁入选”，只负责把数字翻译成运营人员能看懂、能用于汇报的文字。

输入：

```json
{
  "segment_name": "candidate_installment",
  "count": 2000,
  "avg_monthly_spend": 7820,
  "high_spend_ratio": 0.74,
  "app_active_ratio": 0.68,
  "installment_intent_ratio": 0.41,
  "top_channels": ["app_push", "wechat"],
  "exclusions": {"no_consent": 1200, "frequency_cap": 600}
}
```

输出：

> 该客群共 2,000 人，以高消费且 App 活跃的客户为主，41% 近期表现出分期相关意图；相较短信，App Push 更适合作为首触达渠道。已因未授权和触达过频排除 1,800 人。建议以分期手续费优惠为核心权益，并保留 10% 对照组验证增量转化。

### 优点

- 最安全、最稳定，数字由程序计算，LLM 不碰名单。
- 很适合 B 端界面和答辩：把“看板”变成“策略洞察”。
- 开发速度快，可以立即接到当前项目代码。

### 局限

- 它不是“自动分群”，而是“自动解释群像”。
- 如果输入统计没有差异，LLM 也不会凭空产生有价值的洞察。

### 开发难度与项目匹配度

难度：低。项目匹配度：必做。它应作为任何其他方案的共同输出层。

## 5. 方法四：自然语言圈选 Agent（LLM 把运营需求变成可执行筛选）

### 它在做什么

运营人员输入一句自然语言：

> 帮我找最近一个月高消费、用 App 比较多、可能对账单分期感兴趣的客户；预算 20 万，投诉风险要低。

LLM 不应直接返回名单，而是先输出受 schema 限制的“圈选 DSL/JSON”，再由后端执行：

```json
{
  "filters": [
    {"field": "monthly_spend", "operator": ">=", "value": 5000},
    {"field": "app_active_days_30d", "operator": ">=", "value": 8},
    {"field": "intent.installment", "operator": ">=", "value": 0.6},
    {"field": "complaint_risk", "operator": "<", "value": 0.2}
  ],
  "required_guards": ["marketing_consent", "frequency_cap", "product_eligibility"],
  "campaign_goal": "installment_conversion",
  "budget": 200000
}
```

后端再将 JSON 编译为参数化 SQL 或对本地数据的安全查询，输出真实人数和群像。

### 为什么它很适合 B 端

它体现了“运营人员不需要写 SQL，也能用自然语言制定策略”。LLM 是策略助理，数据查询和合规校验仍是确定性的系统能力。

### 必须有的安全护栏

1. LLM 只能选预先白名单中的字段和运算符。
2. 用户输入不能直接拼到 SQL 中，必须使用参数化查询。
3. 营销授权、频控、风险规则由服务端强制追加，不能被 LLM 删除。
4. 在显示客户名单前，先展示筛选条件、预估人数和合规检查结果，允许运营人员确认。

### 优点

- B 端产品感最强，演示时很有说服力。
- 能将“需求理解”和“群像刻画”串成一个 Agent 工作流。
- 利用现有的 `intent.py`/策略编排代码即可先做原型。

### 局限

- 需要维护字段字典、JSON Schema 和查询转换器。
- 它并不会自动发现未知群体，而是更高效地执行运营人员已知的需求。

### 开发难度与项目匹配度

难度：中。B 端展示价值：最高。建议作为项目的主要交互入口。

---

## 6. 方法五：LLM 逐客分类（不推荐作为主方案）

### 它在做什么

把每个客户的画像和事件摘要交给 LLM，要求判断其属于哪一个预定义客群：

```text
输入：客户画像 + 近 10 条行为 + 客群定义
输出：该客户属于“高价值分期潜力客群”，置信度 0.82，理由是……
```

### 适用条件

- 客户量很小，只想做 Demo。
- 客户信息中有大量文本、规则又很难写全。
- 需要人工复核，而非自动批量投放。

### 为什么不推荐用作银行营销的主链路

- 对同一输入可能出现不稳定输出。
- 大量逐客调用很慢、成本高。
- 对数值门槛、频控、授权判断不如规则可靠。
- 很难严格审计“为什么第 1001 个客户被选中”。

结论：可用于“辅助打标签”或 Demo 展示，不用于最终名单准入。

---

## 7. 方法六：RAG + LLM 策略诊断（让群像会“回答问题”）

### 它在做什么

给 LLM 配置受控工具：

- `get_segment_profile(segment_id)`：查询群像统计。
- `get_product_rules(product_id)`：查询产品规则。
- `get_channel_performance(channel)`：查询历史渠道表现。
- `get_compliance_rules()`：查询合规规则。

运营人员追问：

> 为什么不建议对这批人发短信？如果预算缩减到 10 万，策略怎么调？

LLM 先调用工具拿到真实数据与规则，再给出基于证据的解释和重算请求。RAG 负责“查到正确的业务知识”，LLM 负责“理解问题、组织调用和解释答案”。

### 它与群像的关系

它不负责创建客群，而是让已生成的群像可追问、可解释、可做方案模拟。对于答辩，它会让 B 端从普通看板升级为“智能运营策略助手”。

### 优点与局限

- 优点：Agent 感很强，能自然衔接知识库、策略、预算、合规。
- 局限：需要先有可靠的接口与数据；要限制工具权限和回答依据，不能让它编造指标。

难度：中到高。建议作为最后的加分项。

## 8. 六种方法的横向选择

| 方法 | LLM 的角色 | 是否真正自动发现群体 | 是否适合上线准入 | Demo 效果 | 实现难度 |
| --- | --- | --- | --- | --- | --- |
| 1. 结构化信息抽取 | 读懂文本，抽取标签/意图 | 间接 | 是，需阈值与规则复核 | 高 | 低-中 |
| 2. 向量 + 聚类 + LLM 命名 | 理解语义、命名并解释聚类 | 是 | 否，需叠加规则 | 很高 | 中 |
| 3. 群像报告生成 | 解读统计、生成运营语言 | 否 | 是，因名单由确定性逻辑产生 | 高 | 低 |
| 4. 自然语言圈选 Agent | 将需求编译为筛选条件 | 否 | 是，服务端强制合规 | 很高 | 中 |
| 5. 逐客分类 | 给客户归类和解释 | 仅限预定义群 | 不建议 | 中 | 低-中 |
| 6. RAG 策略诊断 | 查询知识和解释/模拟 | 否 | 不直接做准入 | 高 | 中-高 |

## 9. 给本项目的三套可选组合

### 方案 A：稳妥可交付型

```text
规则/评分圈选 -> 方法 3 群像报告生成 -> B -> C 策略包
```

适合：时间紧、现有主要是表格 mock 数据、希望先把系统主链路跑通。

你能展示：客群选择、合规排除、可解释群像、渠道与预算策略、复盘。

不足：LLM 的“数据理解”亮点较弱，主要用于解释。

### 方案 B：推荐的平衡型

```text
项目三对话/搜索文本
    -> 方法 1 抽取意图标签
    -> 规则/评分圈选
    -> 方法 3 生成群像报告
    -> 方法 4 自然语言圈选 Agent
    -> B -> C 策略包
```

适合：你们希望既有真正的 LLM 输入，也有可靠的银行营销决策链路。

你能展示：客户一句咨询如何变成意图标签，如何影响 B 端圈选，运营人员如何用自然语言改策略，系统如何给出可解释群像。

这是我最推荐的方案。它的复杂度可控，三人协作边界也很清楚：项目一维护知识与画像，项目二做意图消费、圈选和策略，项目三产生客户文本与反馈。

### 方案 C：算法展示型

```text
项目三对话/反馈文本
    -> 方法 1 抽取结构化标签
    -> 方法 2 向量 + 聚类自动发现主题人群
    -> 规则/风险/价值二次筛选
    -> 方法 3 群像解释 + 方法 6 策略追问
```

适合：有较多模拟文本或真实脱敏文本，答辩想突出算法创新。

你能展示：系统发现“分期费用关注”“商旅权益咨询”“负反馈敏感”等未预设群体，并自动生成策略。

不足：工作量最大，数据量不足时聚类结果会显得牵强。

## 10. 我建议你现在选择什么

建议选择 **方案 B（平衡型）**，并按下面的最小闭环实现：

1. 定义 8-12 个意图/行为标签，例如 `installment_interest`、`travel_interest`、`benefit_interest`、`do_not_contact_signal`。
2. 用 LLM 将 C 端对话摘要转为严格 JSON 标签，保留原文证据和置信度。
3. B 端采用“授权/频控/投诉风险过滤 + 价值/意图/渠道多维评分”形成确定客群。
4. LLM 根据群体统计生成 `audience_profile` 和 `business_interpretation`。
5. 运营人员用自然语言提出策略目标，LLM 生成受限筛选 JSON；后端验证并执行。
6. C 端回传点击、转化、拒绝和投诉，B 端对比策略组/对照组并更新下一轮策略。

它不是“让 LLM 随便决定谁能被营销”，而是让 LLM 在它擅长的地方增强系统：读懂客户、理解运营语言、解释群像、协助策略。精确决策仍由数据、规则和模型共同保证。

## 11. 你可以这样向老师介绍

> 我们没有把大模型当作黑盒筛人器，而是采用“LLM 语义理解 + 可审计规则与评分 + 可解释策略生成”的混合架构。LLM 从客户对话和行为文本中抽取实时意图，策略引擎在授权、频控、风险和产品规则约束下形成客群，LLM 再把群体统计转成运营可读的画像与策略建议。这样既体现大模型的语义能力，也保证了银行营销中的可控、可解释与合规。
